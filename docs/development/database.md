# Local Database Workflow

## Design

`compose.yaml` is the portable source of the local PostgreSQL service and the optional full-stack
containers. On Windows, `scripts/compose.ps1` is a project hook that:

1. Auto-detects a running Docker engine or the validated Podman Desktop machine.
2. Allows an explicit `COMPOSE_PROVIDER=Docker|Podman` override.
3. Uses Docker's installed Compose plugin without Python or `uv`.
4. Runs pinned `podman-compose` 1.6.0 through `uv` only for the Podman path.
5. Waits for the Compose health checks.
6. Tests the published Windows database port.
7. Falls back to the current Podman WSL address when localhost forwarding is unavailable.
8. Writes the usable connection to ignored `backend/.env.compose`.

Database startup and logs explicitly target `postgres`, so tests and host development do not build
or start the application containers. Status shows the entire named project because provider support
for service-filtered `ps` is inconsistent. Full-stack `app:*` commands use the same hook and Compose
project; database reset still tears down the project before deleting its one named data volume.

An MCP server was intentionally not introduced. The project needs deterministic process execution, not a long-running protocol adapter or another security boundary.

## Commands

- `npm run db:prepare`: start PostgreSQL, migrate to head, and seed missing evaluation data.
- `npm run db:up`: start PostgreSQL and generate the runtime connection file.
- `npm run db:status`: show the Compose project containers.
- `npm run db:logs`: show the latest 100 database log lines.
- `npm run db:migrate`: apply all pending Alembic revisions.
- `npm run db:seed`: add only missing stable evaluation records.
- `npm run db:down`: stop the project and preserve its named volume.
- `npm run db:reset`: stop the project, delete its named database volume, and start empty PostgreSQL.
- `npm run app:build`: build the locked backend runtime and production frontend assets.
- `npm run app:up`: build and start PostgreSQL, FastAPI, and Nginx, then wait for all health checks.
- `npm run app:status`: show all three Compose services.
- `npm run app:logs`: show the latest 100 lines from all three services.
- `npm run app:down`: stop all three services while preserving PostgreSQL data.
- `npm test`: recreate, migrate, seed, test, and drop the isolated `elite_dev_test` database.
- `npm run test:e2e`: do the same for `elite_dev_e2e` while Playwright runs the cross-role browser flow.

After `db:reset`, run `npm run db:migrate` and `npm run db:seed`, or use `npm run db:prepare`.

`app:up` normally publishes `localhost` URLs. When Podman's WSL ports are not forwarded to
localhost, the hook can use the current machine address for host access, align `VITE_API_URL` and
`FRONTEND_ORIGIN`, and print the reachable URLs. A missing Windows-to-WSL LAN forward cannot be
created by application configuration; the phone-testing fallback is documented in
`TROUBLESHOOTING.md`.

## Migration Workflow

The current migration head is `91ec7f95d3b1`. For a reviewed future model change:

```powershell
uv --directory backend run alembic revision --autogenerate -m "describe change"
uv --directory backend run alembic upgrade head
uv --directory backend run alembic check
```

Autogenerated migrations must be reviewed before application. Model metadata and migration history are both versioned; `alembic check` detects drift between them.

## Existing PostgreSQL Without Containers

Docker and Podman are conveniences for reproducible local infrastructure, not persistence
dependencies in the application. Any PostgreSQL instance reachable from the host can be used,
including an existing local installation or a separately managed server.

Set `DATABASE_URL` in the process or `backend/.env` to a Psycopg SQLAlchemy URL, then run Alembic and
the seed directly:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://app_user:app_password@localhost:5432/elite_dev"
uv --directory backend run alembic upgrade head
uv --directory backend run python -m backend.database.seed
```

The target database and login must already exist and allow schema creation. Do not run
`db:prepare` for this path because that command deliberately starts the project Compose service.
Process environment variables take precedence over both backend environment files.

## Data Safety

The local `elite` / `elite` credential is deliberately non-secret and must never be reused outside local development. `db:down` is recoverable because it preserves the volume. `db:reset` irreversibly deletes only the Compose volume owned by `elite-dev-challenge`.

Process environment variables take precedence over local files. A user-managed `backend/.env`
takes precedence over the generated `backend/.env.compose` file.

The isolated-database helper accepts only `elite_dev_test` and `elite_dev_e2e`, connects through the project-generated URL, terminates connections only to that named database, and then recreates or drops it. It refuses any other database name. This protects the persistent `elite_dev` development database from automated test cleanup.
