# Functional Requirements

## Product Goal

Build an event and ticketing platform where an organizer publishes local events derived from an external catalog, a customer reserves and purchases tickets, and gate staff validates those tickets at event entry.

## Actors

### Organizer

- Authenticates with the Organizer role.
- Searches the Ticketmaster catalog through the backend.
- Selects an external catalog item as source material for a local event.
- Defines the local date, location, capacity, and price.
- Creates, lists, edits, and publishes only their own events.

An analytics dashboard is not mandatory. Minimal event-management screens are sufficient.

### Customer

- Authenticates with the Customer role.
- Browses and performs basic text search over published local events.
- Views event date, location, price, and availability.
- Selects a ticket quantity for general admission.
- Creates a temporary inventory hold.
- Completes a deterministic simulated payment that can be approved or declined.
- Views issued tickets and their QR codes in a "My Tickets" area.
- Shares a ticket through a bearer link generated by the application.

Basic text search is mandatory. Advanced filters are optional.

### Gate Staff

- Authenticates with the Gate role.
- Selects the event being validated.
- Reads a QR code through a browser camera.
- Enters the ticket code manually when camera access is unavailable.
- Receives one clear result: valid, invalid, already used, or wrong event.

## External Catalog

- The backend calls the Ticketmaster Discovery API and keeps its credential secret.
- External responses are normalized before reaching the frontend.
- A local event stores a snapshot of the selected catalog item.
- A published local event remains usable when Ticketmaster is unavailable or changes its data.

## Reservations and Payments

- Inventory is quantity-based; numbered seats are outside the mandatory scope.
- A pending reservation holds inventory for ten minutes by default.
- The PostgreSQL clock is authoritative for expiration.
- An unexpired hold reduces availability for other customers.
- An expired or declined reservation releases its held quantity.
- An approved payment atomically finalizes the reservation and issues one ticket per purchased unit.
- Repeated payment requests must not issue duplicate tickets.
- Concurrent reservations and payments must never exceed event capacity.
- No real financial transaction occurs.

## Tickets and Sharing

- Every issued ticket has a persistent, versioned HMAC-signed token.
- The QR code and sharing link carry the same verifiable ticket credential.
- The token does not expose personal customer data.
- A shared link reveals only the minimum information required to present the ticket.
- Copying a valid bearer link is possible by design; fabricating a different valid token is not.

## Gate Validation

- Signature verification happens before ticket state is trusted.
- Validation occurs in the context of a selected event.
- A valid, unused ticket for the selected event is marked as used atomically.
- An unknown or tampered token returns invalid.
- A valid ticket for another event returns wrong event.
- A previously consumed ticket returns already used.
- Concurrent validation attempts can accept the ticket at most once.

## Authentication and Authorization

- The application has three distinct roles: Organizer, Customer, and Gate.
- A user has one role in the mandatory scope.
- Organizers access only their own event-management resources.
- Customers access only their own reservations and private ticket collection.
- Gate users validate published events.
- Public registration, password recovery, and email delivery are not required.

## Required Seed Data

The seed process must create:

- One organizer.
- Two customers.
- One gate user.
- At least one published event with available inventory.
- Stable credentials documented for evaluation.

## Explicitly Excluded

- Fiscal invoices.
- Ticket resale between users.
- Native mobile applications.
- Password recovery.
- Ticket delivery by email.
